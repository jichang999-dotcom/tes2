방법

②변경 사항 목록마지막 커밋 뒤에 바뀐 파일. 오른쪽 글자 M = 고침 · U = 새 파일 · D = 지움
③파란 「커밋」 버튼누르지 않습니다 — 커밋은 카드대로 Claude 에게 시킵니다
④파일 옆 되돌리기 화살표누르면 그 파일의 고친 내용이 바로 사라집니다. 누르지 않습니다
⑤그래프커밋 목록. 위가 최신이고, main 표시가 지금 내가 있는 자리
내가 시키지 않은 파일이 변경 사항에 있으면 그 파일을 눌러 무엇이 바뀌었는지 본 뒤 Claude 에게 「이 파일은 왜 바뀌었어? 아직 아무것도 하지 마」라고 묻습니다. 3단계 프롬프트는 git_practice 의 메모.txt 만 커밋하므로, 다른 파일이 남아 있는 것 자체는 정상입니다.
4

되돌리기

방법
git_practice 의 메모.txt 에서 그 줄을 일부러 「Git 연습: 실수」로 바꿔 「연습: 실수」 메시지로 커밋해 줘. 그다음 방금 커밋을 되돌려 줘. 기록은 지우지 말고 되돌리는 커밋을 새로 만들어(git revert). 그 파일 내용과 git log --oneline -4 를 보여 줘.
확인

파일이 「첫 수정」으로 돌아왔고, 목록 맨 위에 Revert "연습: 실수" 가 있다.

주의사항 (2)
주의「기록까지 지우는 되돌리기」(git reset --hard)는 시키지 않습니다. 지운 기록은 다시 못 찾습니다.
4단계를 마친 뒤 「소스 제어」 화면
번호보이는 것뜻
①변경 내용이 비어 있음되돌리기까지 모두 커밋돼서 남은 변경이 없습니다. 아이콘 위 숫자도 사라집니다
②파란 「게시 Branch」 버튼변경이 없으면 커밋 버튼 대신 나옵니다. 누르지 않습니다 — GitHub 올리기는 7 · 8단계
③Revert "연습: 실수" + main되돌리기도 새 커밋 하나입니다. 맨 위가 지금 상태이고, 파일 내용은 「첫 수정」과 같습니다
④연습: 실수실수한 커밋이 지워지지 않고 남아 있습니다. 그래서 무엇을 잘못했는지 나중에도 볼 수 있습니다 — 이것이 git revert 가 안전한 이유입니다
5

브랜치

방법
git_practice 저장소에 test 브랜치를 만들어 거기서 메모.txt 에 「브랜치에서 쓴 줄」을 추가하고 커밋해 줘(그 파일만 · 다른 저장소는 건드리지 마). main 으로 돌아와서 그 파일에 그 줄이 없는 것을 보여 주고, git diff main test 로 두 브랜치의 차이를 보여 줘. 합치지는 마.
확인

git branch 에 main · test, 지금은 main 이고 파일에 그 줄이 없다.

주의사항 (3)
브랜치는 언제 쓰나요잘 돌고 있는 스크립트를 크게 고쳐 볼 때. test 에서 고쳐 보고, 괜찮으면 main 에 합치고, 아니면 버립니다. main 은 그동안 멀쩡합니다.
주의브랜치를 바꾸기 전에는 저장 안 한 수정이 없어야 합니다. 「저장 안 한 변경이 있다」고 하면 먼저 커밋하거나 Claude 에게 「어떻게 할지 물어봐 줘」라고 합니다.
5단계를 마친 뒤 화면
번호보이는 것뜻
①왼쪽 그래프에 test 커밋이 없음그래프는 기본으로 지금 있는 브랜치(main)만 보여 줍니다. test 커밋이 사라진 것이 아닙니다
②+브랜치에서 쓴 줄git diff main test 결과. main 과 비교해 test 에만 이 한 줄(+)이 더 있습니다
③브랜치 상태 * main · test브랜치가 두 개이고, * 표시가 지금 있는 브랜치(main)입니다. 두 브랜치는 합치지 않았습니다
직접 확인해 보기 VS Code 왼쪽 아래 상태 표시줄의 브랜치 이름(main)을 눌러 test 로 바꾸면 파일에 그 줄이 다시 나타나고 그래프에도 test 커밋이 보입니다. 다 봤으면 다시 main 으로 돌아옵니다.

올리기 (push)

방법

[입력] 칸을 내 것으로 채워 붙여넣습니다.

워크스페이스 저장소를 7단계에서 만든 GitHub 비공개 리포에 올려 줘(main 브랜치만). 1. 리포 이름: [입력 — 7단계에서 정한 리포 이름] 먼저 올라갈 파일 목록(git ls-files)을 보여 줘. .env · data 폴더 · CSV · 엑셀 파일, 사람 이름이나 연락처가 든 파일이 있으면 멈추고 알려 줘. 내 GitHub 아이디는 gh api user --jq .login 으로 직접 확인해. git remote -v 에 원격이 없으면 https://github.com/<내 아이디>/<리포 이름>.git 로 git remote add origin 하고, 이미 있는데 그 주소가 아니면 바꾸지 말고 멈춰서 주소를 보여 줘. 맞으면 git push -u origin main 해 줘. 로그인 창이 뜨면 내가 브라우저에서 로그인할게. 비밀번호나 토큰을 대화창에 묻지 마. push 가 끝나면 gh api repos/<내 아이디>/<리포 이름>/commits/main --jq .author.login 으로 최신 커밋이 내 GitHub 아이디와 이어졌는지 보여 줘. 비어 있거나 null 이면 Git 메일과 GitHub 메일이 다른 것이니 git config --global user.email 값과 함께 알려 줘.
확인

GitHub 리포 화면을 새로고침하면 코드 · 설정 파일만 보이고 데이터 · .env 는 없다. 마지막 결과에 내 GitHub 아이디가 나온다(비어 있거나 null 이면 6단계 팁).

방법

웹훅 만들기

Claude 없이 슬랙 화면에서 직접 만듭니다. 빨간 테두리를 차례로 누르면 됩니다.

방법
  1. api.slack.com/apps → 오른쪽 위 Create New App → 아래 「From scratch」의 Pick features → Continue.
  2. App name = <영문 이름>-alert(예 hong-alert) · Workspace = 13단계에서 만든 <내 이름>-ax → Continue.
  3. 검색 칸에 incoming-webhook 을 치고 나온 줄을 눌러 추가 → Continue.
  4. 다음 창(「What it can respond to」)은 아무것도 넣지 않고 Continue.
  5. Create and Install → 허용 화면에서 보낼 채널 = #알림 → 허용.
  6. 앱 설정 화면 왼쪽 Incoming Webhooks → 아래 목록의 Webhook URL(https://hooks.slack.com/services/…) 옆 Copy.
  7. VS Code 왼쪽 탐색기에서 워크스페이스 폴더의 .env 를 엽니다(없으면 새 파일 .env). 한 줄 SLACK_WEBHOOK_URL_EDU= 을 적고 그 뒤에 붙여넣은 뒤 저장(Ctrl+S).
확인

주의사항 (3)
주의.env 에 이미 있는 이름(예 SLACK_WEBHOOK_URL)으로 한 줄 더 적지 않습니다. 같은 이름이 두 줄이면 뒤 줄이 이겨서, 그 이름을 쓰던 다른 자동화 알림까지 실습 채널로 갑니다. 실습 주소는 SLACK_WEBHOOK_URL_EDU 처럼 새 이름으로 적습니다.
앱 이름은 영문으로슬랙 앱 이름은 영문 · 숫자 · 띄어쓰기 · - · 괄호만 됩니다(2026-11 화면). 한글 이름은 넣지 않습니다.
주의웹훅 주소는 Claude 대화창에 붙이지 않고 .env 에만 넣습니다. 주소를 아는 사람은 누구나 그 채널에 글을 쓸 수 있습니다.
